# 本地安全模型

本文描述 ATM 当前实现实际提供的防护边界。它是本地单用户桌面应用的安全契约，不是互联网多租户服务的威胁模型。

## 受保护的边界

### 服务发现与调用认证

- daemon 只监听 `127.0.0.1`，API 使用运行时选择的独立端口；`9999` 仅是 e2e 用的 Vite 前端端口。
- 正式桌面 daemon 每次启动都会生成新的 Bearer token，并原子发布到 `%LOCALAPPDATA%\AyanamiTaskManager3\runtime\daemon.json`（设置了 `ATM3_DATA_DIR` 时在它下面）。发现文件同时绑定 `endpoint`、`pid`、`version`、`startedAt` 和随机 `instanceId`；正常退出会清除它，旧 token 在重启后失效。只用于测试与开发的 standalone daemon（`apps/daemon`，2.x 的 TS 实现）仅在显式设置 `AYANAMI_TASK_TOKEN` 时允许固定测试 token，3.0 的原生宿主不读这个变量。
- 自动安装的 Agent 配置使用 stdio bridge，bridge 每次请求都重新读取并校验发现文件，因此配置不持久化 endpoint/token，也能跨 daemon 重启恢复。
- REST 在认证前拒绝非 localhost/127.0.0.1 的浏览器 `Origin`；错误响应不回显当前或调用方提供的 token。3.0 不再提供 WebSocket 事件流（`/api/v1/ws` 返回 404），界面定时重新读取。2.x 与 standalone 开发 daemon 的事件流规则是：WebSocket 必须在 3 秒内完成认证；错误 token 或超时以 `1008` 关闭，认证成功前不发送业务事件。认证前的非法 JSON 只返回有界协议错误，不会得到业务数据。
- 打包 Renderer 不接收原始 endpoint 与任何令牌，只通过宿主注入的有界 `window.ayanamiDesktop` capability 访问 `/api/v1/*`（宿主只接受入口文档、白名单方法、类型正确的参数，再交给宿主进程内的 ui-bridge 分发）；跨源导航和新窗口被拒绝。生产宿主不开 WebView2 调试端口，并清掉试图从环境变量注入的浏览器参数。设置页为“复制当前运行实例的 Streamable HTTP 配置”取得的配置里带的是 Agent 凭证。

Bearer token 是本地调用认证凭据。不要把它写入仓库、日志、ATM Record、对话、命令行参数或长期 Agent 配置。只有用户明确复制“当前运行实例”的 Streamable HTTP 配置时，该临时配置才会包含当前 token。

### 用户凭证与 Agent 凭证

3.0 只有一个令牌，每次启动重新生成：

- **Agent 凭证**：即 `daemon.json` 里的 `token`。MCP bridge（`atm-mcp.exe`）、`--cli` 和按指南直接调 REST 的 Agent 都用它。
- **User 主体**：不是令牌。界面请求经宿主注入的 capability 进入宿主进程内的 ui-bridge，由它以 User 身份分发给服务；User 主体只在 ui-bridge（WebView、托盘）和测试用的 e2e 适配器里构造，不存在可被读取或复制的用户令牌。

「用户的决定」只接受 User 主体，Agent 凭证调用返回 `403 USER_AUTHORIZATION_REQUIRED`，且不产生任何写入；CLI 对其中的备份新建与恢复、导出、导入应用、项目归档与恢复在本地直接拒绝（退出码 3），不发请求。包括：垃圾箱恢复请求的授权与拒绝，项目恢复、移入垃圾箱与归档，新建与恢复备份（新建会按保留策略删除同组最旧的手动备份），设置写入，保存视图的新建、修改与删除，知识的新建、更新与归档（REST 这几条是管理界面入口：不记 Agent 作者、不要求 Session、能改已归档条目；Agent 发布知识走 MCP `atm_knowledge_save`，作者记为该 Agent），导入 apply，项目路径绑定，Session 强制关闭，`/projects/:code/ui/*` 与其他以用户身份落账的写入，以及 `actor=USER`（含缺省）的临时任务写入。

3.0 的归类由能力目录（`apps/desktop/native/domain/src/capability.rs`）决定：每个服务入口在任何副作用之前先核对主体的能力，表里只给 User 的写能力合起来就是用户专属集合；Agent HTTP 上对应的 2.x 路由是统一的拒绝桩，不读 body、不碰服务。这保证每个入口都过同一道检查，但每项能力**归哪一边**仍是人为判断：目录不证明给 Agent 的能力行为无害，2.x 时曾被写成「只新增一份备份」的备份路由实际会淘汰用户的手动备份，就是靠复核实测发现的。

这一层挡住的是「按文档办事的 Agent」和「读一个文件就能冒充用户」：只持 MCP/bridge，或读取 `daemon.json` 后直接调 REST 的 Agent，都无法替用户授权。它**不是**同用户进程之间的强隔离：同一 Windows 用户下的程序仍可以蓄意读取 ATM 主进程内存，或模拟键盘鼠标操作界面，这两类仍属于下文的非目标。standalone 开发 daemon（`apps/daemon`）只有显式设置 `AYANAMI_TASK_USER_TOKEN` 时才分离凭证，否则那一个 token 同时代表用户，不应用于安装版。

### 手机同步与自建中继（可选，默认关闭）

设计与协议见 [mobile-sync.md](mobile-sync.md)，决策见 [ADR-017](adr/ADR-017-mobile-relay-and-dispatch.md)。

- **不新开监听端口。** 同步连接器在 daemon 进程内只做出站 HTTPS，连接用户自己配置的中继；daemon 仍然只监听 `127.0.0.1`。中继地址只接受 https，明文 http 只允许 `127.0.0.1` / `localhost`（开发联调）。
- **仓库与安装包里没有默认服务器。** 未配置中继时连接器不发任何网络请求；守卫扫描生产代码，出现维护者自己的服务器域名即红。
- **中继是不可信传输层。** 每个配对空间有一把 32 字节空间密钥，经 HKDF 派生出 AES-256-GCM 与 HMAC 两把子密钥；所有文档内容端到端加密，AAD 绑定文档键，项目码经 HMAC 后才进键名。中继运营者或拿到中继 token 的人能看到键名、大小与时间，能删改或重放密文、拒绝服务，但读不到内容，也伪造不出能通过校验的命令。
- **密钥不进 Agent 可读的地方。** 中继 token 与空间密钥由宿主进程内的 `atm-sync` 直接调 Windows DPAPI（当前用户）加密，落在 `%LOCALAPPDATA%\AyanamiTaskManager3\data\sync\secrets.dpapi.json`（文件格式与 2.x 相同，转换后原样可用），启动自检不通过就拒绝保存、绝不退回明文；3.0 没有明文形态。standalone 开发 daemon（`apps/daemon`）用明文文件并在状态里标明。两者都不写入库里的 settings 表、`daemon.json`、日志或 ATM Record。`GET /api/v1/sync/status` 两种凭证都能读，但不含 token、空间密钥或配对码。
- **写入口全部是用户专属。** 修改中继配置、生成配对码、重置配对都要求用户凭证；Agent 凭证返回 `403 USER_AUTHORIZATION_REQUIRED`。配对码同时携带中继 token 与空间密钥，只在设置页本地展示。
- **手机只能发白名单命令。** 仅「建任务」与「对已有任务派单」两种；命令 ID 同时是幂等键（`op_id = mobile:<命令 ID>`），重放不会建第二个任务；早于 7 天的命令被拒。建出的任务以 USER 身份落账，与在桌面端点「新建任务」等价。
- **撤销。** 「重置配对」轮换空间 ID 与密钥并删除旧空间里的全部文档，旧手机随即无法解密新数据；吊销中继 token 属于中继自身的管理动作。

### Claude 自动派单（可选，默认关闭）

- 只处理用户明确点名的任务：手机新建任务时勾选「交给 Claude」、对已有任务点「交给 Claude」，或桌面端任务抽屉里的同名按钮。ATM 不会自己挑任务派出。
- 开关、权限模式、并发上限、模型等配置只能用用户凭证修改；默认权限模式 `auto`，`bypassPermissions` 需要用户在设置里显式选择。
- 会话以参数数组启动 `claude -p`（不经 shell），提示词经 stdin 传入且不含任何密钥；子进程环境去掉会把会话串到宿主上的 Claude Code 会话变量。会话日志只写 `%LOCALAPPDATA%\AyanamiTaskManager3\data\dispatch\logs`，不进入项目事实。
- **一条手机命令最多起一次会话。** 手机命令的 ID 作为派单的 `requestId`，派单层把「命令 ID → 那次派单 / 被拒原因」写进库里的 `dispatch_requests` 表，与派单记录 `dispatch_runs` 在同一个写事务里、在起进程之前落盘，保留 9 天（盖住 7 天有效期与手机时钟偏差）；保留期内满 2000 条就拒收新的手机派单而不是挤掉旧条目。中继把旧密文原样放回、或 ack 写失败后整条重做时，只会拿回当初那次派单（即使它已失败或取消、任务又能派了），不会再起一次 Claude。同步侧的已处理集合也按命令 ID 内嵌的时间保留到有效期之后，而不是只留最近若干条。
- **账本出问题时宁可拒绝也不重派。** 账本读不出来（库报错）时手机派单一律 503 拒绝，读得出来后自动恢复；转换时 2.x 的账本文件坏了、库里有读不懂的条目，或整库恢复时当前库读不出来（拿不回账本）时，设下持久化的丢失水位线：账本里查不到、且发送时间不晚于水位线（或取不出发送时间）的命令一律拒绝并提示用户在手机上重新交给 Claude，拒绝本身不记账；派单历史里存着每次手机派单的 `requestId`，据此补回的条目照常精确回放。水位线 9 天后自动清除，桌面设置页在此期间给出提示。
- **不对身份不明的进程动手。** spawn 后立刻记下系统给的进程出生标识（Windows：创建时刻 FILETIME 原值，100ns 整数；Linux：`/proc/<pid>/stat` 的 starttime 加开机 ID；其它平台拿不到可靠标识，一律视为未知）；本宿主起的会话靠进程句柄判断存活。宿主重启后只有记下的与现查的标识都已知且**逐字相同**才接管该 PID，没有任何时间容差；接管后每次轮询、每次取消前都重核；对不上按「原进程已退出」处理，核验不了就停止跟踪并把派单记为失败、提示用户自己去任务管理器处理——任何情况下都不会对身份不明的 PID 执行 `taskkill /T /F`。日志里有没有 result 行不作为身份依据；旧版本只存了 ISO 创建时间的记录一律按未知处理。核验与结束之间仍有极短的复用窗口（接管的进程没有句柄可持），这是已知残余风险。
- **取消以进程真正结束为准。** taskkill 成功或进程已不存在（退出码 128）才记为取消并释放并发名额；结束失败时派单保持运行、名额不释放，接口返回 500 `DISPATCH_CANCEL_FAILED`（可重试，带中文原因），界面原样显示。

### Cursor 完整性与作用域

Task、Record、Session、Search 和长字段 cursor 包含版本、选择条件、项目/实体、范围世代、快照位置与内容摘要。读取端会拒绝损坏、跨项目、跨实体、跨选择集复用、内容已变化或范围已被恢复过的 cursor。

2.x 的 cursor 摘要是确定性的完整性与作用域绑定，不是带秘密密钥的签名、MAC、认证或授权，持有代码的调用方可以重算。3.0 改为用库内随机生成、不出库的密钥（`app_meta.cursor_key`）对 cursor 算 HMAC-SHA256（取前 16 字节），只靠代码已算不出；但同一 Windows 用户下能读数据库的程序仍拿得到这把密钥，所以它同样只用于损坏检测与作用域绑定，不是访问控制。访问权限仍由 Bearer token 和上层业务规则决定。

### 受管路径与迁移

- 2.x 数据根迁移脚本（`pnpm migrate:data-root`）要求正式数据根是有界绝对路径；迁移拒绝盘符根、相同/嵌套根，以及把 symlink/junction 直接作为源或目标根（`DATA_ROOT_LINK_NOT_ALLOWED`）。源、目标或备份根内的 `runtime` 目录也不得是 symlink/junction（`DATA_ROOT_RUNTIME_LINK_NOT_ALLOWED`）。
- 迁移复制时不跟随数据根内的 symlink/junction，尤其不会展开指向完整安装目录的 `current` junction。
- 导出、导入、备份、按范围恢复、附件访问在第一个副作用之前，从数据根往下逐层钉住要碰的目录（`exports`、`exports\.staging`、库目录下的 `artifacts`、`artifacts\.restore-staging`、`artifacts\.restore-old`、项目附件目录）：任何一层是 symlink/junction 就拒绝（`BACKUP_INTEGRITY_FAILED`，`reason: LINKED_PATH`），包括上一次恢复的收尾清理在内什么都不做；钉住的目录在操作结束前改不了名、删不掉，链不会中途被换掉。数据根以上的链接（把整个目录挪到别的盘再链回来）不受影响：那只是数据根换了位置，ATM 碰的仍是这个数据根里面的东西；钉住之后的读写一律从数据根的真实位置拼路径，不再经过那条链接，所以操作中途把它换成指向别处的链接也带不走任何写入或删除。还不存在的层（第一次导出时的 `exports`、第一次换入附件时的 `.restore-old` 等）相对上一层的句柄排他新建，建出来就钉着。备份根同样处理（`.withdrawn`、`.creating` 是链接时创建、撤回、清扫都拒绝）。附件访问交给调用方的项目目录先核验、钉住；项目不存在时不建目录。登记进库的路径（备份目录、附件行）仍是按调用方给的路径写的。导出暂存只清名字是规范 ULID 的条目（ATM 自己起的），认不出的一律留着。
- 钉的时候还不存在、之后才出现的层（比如有人在操作中途把 `backups`、`.withdrawn`、`.restore-staging`、`.restore-old` 建成指向别处的 junction）：清扫、收尾、备份、导出要枚举、读标记、删除或改名之前再钉一次，新出现的层照样逐层核对，是链接就拒绝；整条链都钉住了才动，否则当作这次没有它。备份与导出的库快照从钉住的数据根里的库文件打开，与附件出自同一个数据根；校验过的备份目录一直钉到恢复结束，校验的和恢复读的是同一份。恢复把暂存换入时，暂存目录按句柄打开（不跟随链接、不共享删除），核对它是普通目录、就在钉住的 `.restore-staging` 里，然后按这个句柄改名：核对之后到改名生效，别人改不了它的名，也换不成链接。Store 打开时就钉住数据根（库所在目录，跟随链接解析一次），整个生命周期持有：写连接、读池、checkpoint 从它的真实位置打开，附件守卫、备份根与旁路读也从它往下钉，钉住后再核对一次是同一个目录；打开之后再把数据根以上的链接换向，换不走这个 Store 读写的数据根。内部路径一律用 `\\?\` 完整写法：超过 MAX_PATH 的数据根与名字以空格结尾的目录经 SQLite 备份、导出、恢复全流程验证可用；名字以点结尾的目录只验证过目录链与文件读写，SQLite 打不开放在这种目录里的库，所以数据根路径上不支持以点结尾的目录名。对外显示和登记的仍是调用方给的写法。调用方给的备份根、导出目录、登记的备份目录在数据根之下时，换算到 Store 钉住的真实位置里再钉；「在数据根之下」按 Windows 的同一位置判断：任何写法先经 `RtlDosPathNameToNtPathName_U_WithStatus`（CreateFileW 用的同一步）换成 NT 路径，`/`、`.`、`..`、连续分隔符与 `\\?\`、`\\.\`、`\\?\UNC\`、`\\.\UNC\`、`\\` 几种前缀都由它按 Win32 的规则处理；只认 `\??\X:\…`（盘符）与 `\??\UNC\…`（共享）两种结果。盘符不按字母比，也不按 `QueryDosDeviceW` 给的字符串比，每一步都要有确定的结论：subst 换成它指向的路径再判断，最多 4 层；映射的网络盘只认格式完全对得上的 LanmanRedirector（含经 Mup 的）目标，换成对应的 `\\server\share`（只去掉重定向器自己打头的段，之后的名字原样），其余重定向器（WebDAV 等）与解析不了的目标拒绝；其余的盘符必须是挂载管理器登记的卷的根（`GetVolumeNameForVolumeMountPointW` 给出 `\\?\Volume{GUID}\`），按卷名比，同一个卷的两个盘符是同一个位置，指向带路径后缀的设备目标、不是卷、查不到的盘符拒绝。证明不了在不在数据根之下的写法与其余命名空间一样拒绝，不当作外部位置。`\\?\` 写法里的空段在换算盘符之前就定下，换算不会让打不开的写法变得打得开。经本机共享回到本机的 UNC 写法（`\\localhost\C$\…`、本机名、映射到本机共享的盘符）字面上认不出是数据根的哪种写法，服务器名的别名又列举不完，所以按钉住的句柄所在的卷判断：UNC 写法（含映射到网络共享的盘符）钉住的目录，卷序列号与本机任一个卷（`FindFirstVolumeW` 列出的全部卷，含挂在目录上的卷）相同，或本机的卷没能全部读到（枚举失败、中途出错、某个卷读不到序列号；没插盘的可移动卷与没有文件系统的卷不算），就证明不了不在本机，数据根与外部位置都拒绝。序列号碰巧相同的远端共享也会被拒绝；本机的目录要用盘符写。名字用 `CompareStringOrdinal` 不分大小写地比（不做多字符展开）。其余命名空间（`GLOBALROOT`、卷 GUID、设备）判断不了在不在数据根之下：Store 不用这种写法打开；备份根、导出目录、登记的备份目录是这种写法，也在创建、清扫之前就拒绝，不当作外部位置放行。`\\?\` 写法中间有空段（连续的 `\`）的路径 Windows 打不开，同样在创建、清扫之前就拒绝。上面两种结果之外的别名（数据根以外另起的目录链接）按外部位置处理，外部位置照样逐层钉住、是链接就拒绝。
- 2.x 数据根迁移使用目标级独占 lease、staging、manifest、SQLite `quick_check` 和原子 rename；运行时发现文件与旧 token 文件不会进入新数据根或备份。

这些规则保护正常产品入口免于路径别名、嵌套复制和部分提交；它们不把同一用户主动篡改数据库中受信路径视为隔离边界。

### 数据库事务与投影

- 3.0 只有一个库 `data\atm.sqlite`。一个正式 mutation 在一个 SQLite 写事务内同时提交领域状态、单调事件、全局事件流、搜索索引和幂等回执；失败全部回滚。没有 outbox，也没有需要补投的投影。
- `atm_record(kind: "ATM_FEEDBACK")`（旧名 `atm_feedback`）复用同一套 Record mutation：只在本机数据库的当前项目里写入 `ATM_FEEDBACK` Record，不包含网络上传、遥测或自动创建外部 Issue 的路径。
- 生产 SQL 禁止 `ATTACH DATABASE` 后写入被附加的库：3.0 只在按范围恢复读取整库备份、导出与导入项目包、导入 2.x 备份、转换 2.x 数据时，以只读方式（`mode=ro`）附加源库或快照，写入只落在 ATM 自己的库。
- 2.x 的 Registry 投影是可重建读模型，跨数据库不承诺原子可见；3.0 单库之后，总览、项目与搜索在同一事务里可见，这条限制不再存在。

## 明确的非目标

ATM 不试图防御以下主体或场景：

- 与 ATM 处于同一 Windows 用户、能够读取或修改 `%LOCALAPPDATA%` 的恶意进程；
- 已能修改安装文件、注入受信宿主/Renderer、读取进程内存或取得当前用户调试权限的代码；
- 用户主动泄露 Bearer token 后的调用；
- 把本机 loopback 服务直接暴露到局域网或互联网后的安全性（手机同步走出站中继，不需要也不应该这样做）；
- 已配对手机被他人拿到后以本人身份发出的白名单命令，以及中继对密文的删除、回滚与拒绝服务。

若需要跨用户、跨主机或不受信插件隔离，应在 ATM 外部增加操作系统账户边界、文件 ACL、进程隔离和受认证的远程网关，不能把本模型外推为远程安全承诺。

## 自动化守卫

仓库测试绑定以下事实：loopback runtime descriptor schema 与 token 轮换、foreign Origin/错误 Bearer、写入失败整体回滚、随包 Guide/docs 的精确 manifest，2.x 实现上的 WebSocket 认证超时与认证前零业务帧、迁移根 containment 与生产 SQL 无 `ATTACH DATABASE`，以及同步协议的 AAD 绑定、篡改检测、分片提交顺序、命令幂等、同步状态不含密钥、生产代码不含默认中继地址。安装态发布验收还会检查发现文件、旧 token 失效、stdio bridge 和 `%LOCALAPPDATA%\AyanamiTaskManager\docs`。
