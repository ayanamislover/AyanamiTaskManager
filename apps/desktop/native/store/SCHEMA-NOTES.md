## 沿用 05、容易误改的地方

- `restore_guard`（05 §2.7）：知识修订平时不可改、不可删，删除触发器只在这张表有 `KNOWLEDGE` 行时放行。这一行只在恢复事务内插入、提交前删除，其他连接看不到它，所以恢复期间别处的写入依然受约束。不要为了恢复去关触发器。
- `search_fts`（05 §2.5）：外部内容 FTS5，trigram 分词，`content_rowid` 绑定显式的 `INTEGER PRIMARY KEY doc_id`，用 ai/ad/au 三个触发器同步。SQLite 只保证显式 INTEGER PRIMARY KEY 在 VACUUM 后不变，隐式 rowid「可能」被重排，那样索引和内容就会错位，所以 `doc_id` 必须是显式主键。当前打包的 SQLite 实测 VACUUM 并没有重排隐式 rowid，VACUUM 用例因此抓不到这个错，守卫改成直接断言 `doc_id` 就是 rowid 的别名（`tests/search.rs`）。

## 连接参数

`configure()` 对每条连接设置：

- `journal_mode = WAL`：文件库没切成 WAL 就报错（内存库返回 `memory`，不检查）。
- `synchronous = NORMAL`。
- `foreign_keys = ON`：这是连接级参数，默认关闭，漏开时所有复合 FK 都会形同虚设。
- 关闭「双引号回退」（`SQLITE_DBCONFIG_DQS_DML/DDL = 0`，`lib.rs::harden`），写线程、读连接、旁路连接都关。默认情况下找不到的 `"标识符"` 会被悄悄当成字符串字面量：W1f 里一处列名写错，结果把列名本身写进了数据，没有任何报错。关掉之后写错就报错。

`Store::open` 另外设置（`src/engine.rs`，取值依据见 `output/w1-bench/REPORT.md`）：

- `cache_size = -1024`（每条连接 1 MiB page cache，写连接和每个读连接都设）：W1g 在 104 MiB 样本库上的 cache 矩阵（每格一次，有界观测）里 512 KiB～8 MiB 时延看不出差别，内存随之上涨；重复、交错的矩阵留到 W2 性能复核。
- `wal_autocheckpoint = 0`：checkpoint 不在提交里顺手做。写线程每执行完一个作业就通知独立的 checkpoint 线程（只置位），后者做 PASSIVE，两次至少隔 1 s。PASSIVE 放在写线程上时，一次最长 349 ms，期间写入全部排队；只在队列排空时通知，则队列一直有积压时永远没有 checkpoint（W1 peer r1 P1-02）。
- `journal_size_limit = 64 MiB`，同时是 WAL 软上限：读者一直占着快照时 PASSIVE 追不平，WAL 只增不减（实测 30 s 涨到 2.2 GiB）。PASSIVE 报告的帧数超过软上限时，写线程在两个作业之间做一次 RESTART（最多等读者 100 ms）。读者一直重叠、总占着同一个 read mark 时 RESTART 会等满 100 ms 后放弃，下一次 PASSIVE（至少隔 1 s）再试；等读者这一部分让写线程停顿的比例，稳态下约为 10%。这是等待预算的估计，不含 RESTART 成功时的页复制与 fsync，不是总停顿或单次停顿的上限，正式总预算仍需在 W2 测量。放在 checkpoint 线程上做时，积压下它抢不到写锁。这是软上限：复制和 fsync 期间写入排队，峰值取决于写入速度和读者，不是硬上限。
