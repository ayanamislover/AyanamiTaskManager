# 规格追溯（W2 验收，09 §4）

ATM 3 规格（`output/atm3-spec`，不进仓库）的每个规则编号，都要落到用例或明确的后续阶段。检查本身是一条测试：
`cargo test -p atm-service --test spec_trace`，随整套测试每次都跑（09 §4 写的是 `cargo xtask spec-trace`，
做成测试是为了不靠人记得去跑）。

## 输入

- `trace/rules.tsv`：规格编号快照。规格目录不进仓库，所以由开发期脚本 `output/w2-evidence/spec-trace-extract.py`
  从规格抽出提交进来；`--check` 确认快照与规格一致，规格改了忘记重抽会失败。范围：
  - D01–D35（peer r1 的领域规则检查表）；
  - 01–04 的规则 W / S / P / L；
  - 00 §1–§4 被裁决的条目（01/C-xx、01/Q-xx、02/…、03/…、04/C-Lxx；C 编号各节重名，所以带节号）；
  - 10 的 R 条目，R11 拆到子项。
  - 00 §5（05 数据映射）、§6（06 对外面）和 07 的 S/F 编号属于 W3 / W4，不在这里。
- domain / store / service 的全部 `#[test]`：测试名里的 `w052`、`s080`、`p005`、`l112` 自动算作覆盖对应规则；
  `c12`、`r11`、`q01` 这类裁决 token 只校验确实存在（各节重名，覆盖要在下表写明）。
- 下面的映射表。

## 检查什么

- 每个编号要么有用例，要么在下表里有去向；
- 有用例的编号，用例里要同时找得到成功路径和反例的痕迹（`unwrap` / `Ok(` / `Some(` 与 `refused(` / `unwrap_err` /
  `ErrorCode::` / `None)` 等）。纯函数断言常常看不出来，这时说明里必须写「反例：」或「成功例：」并指到具体断言，交给评审核对；
- 测试名引用不存在的编号、表里写了不存在的编号或用例、结论写法不对，都失败；
- 文末生成的 D01–D35 矩阵与汇总要与当前计算一致（`ATM_TRACE_BLESS=1` 重写）。

## 结论

- `COVERED`：W2 已覆盖。
- `PARTIAL(Wn)`：服务层这一半已覆盖，剩下的在 Wn（说明里写剩什么）。
- `SUPERSEDED(编号)`：规格原文被 00 / 10 的裁决改写，用例按改写后的行为断言。
- `DEFERRED(Wn)`：整条属于 Wn（HTTP / MCP / 桥在 W4，界面与合进程在 W5，CLI 与后台在 W6，手机与派单在 W7，转换在 W3）。
- `NA`：裁决是「不做 / 删除 / 作废」或纯文档，没有可测行为。

## 这张表证明什么、不证明什么

检查是**机械的引用完整性**：每个编号都有去向、引用的用例确实存在、用例里有成功与拒绝的痕迹。它不证明某条断言对应的
正是那条规则，也不证明多通道规则的每个入口都接上了——peer W2 r1 用反例推翻过 R2（review_request 漏转移）与
02/C-03（生命周期在幂等裁决前备份）两处 `COVERED`。语义上的确认靠两样：评审逐条核对说明里的「成功例：」「反例：」，
以及 09 §5 的规则变异（`output/w2-evidence/*-mutation-evidence.json`）。W3 拿这张表做迁移对照时，以入口映射与变异
证据为准，不以 `COVERED` 字样为准。
